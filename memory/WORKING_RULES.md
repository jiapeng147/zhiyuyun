# 协作和用户偏好

## 用户要求

- 使用中文沟通。
- 用户说“继续”时，直接开始下一个阶段，不重复询问。
- 用户希望真正改造全套 UI，不接受只改颜色、圆角或几个按钮。
- UI 改造必须尽量保留原功能、API、路由 key、事件逻辑和数据结构。
- 复杂页面逐页迁移，完成一个阶段后构建、部署、冒烟、提交，再进入下一阶段。
- 用户更关注完整商业产品体验，而不是只做演示页。
- 用户反感遗留的 `admin`、旧模板、错位、重复导航、没有响应的按钮。

## 工程做法

- 先读源码和现有模式，再做局部改动。
- 优先复用 `BusinessSection`、`BusinessMetricCard`、`BusinessStatusStrip`。
- 不批量替换高风险表格页。
- 不把未知状态显示成 0、已完成或在线。
- API 失败状态必须在页面上明确显示并可恢复。
- 不伪造商业套餐、支付订单、广告审核或闲鱼成功结果。
- 每个页面改动后同时考虑桌面宽屏、窄屏和移动 Lite。

## 提交规则

每个阶段尽量保持：

1. 单阶段、单目的 diff。
2. `npm run lint`。
3. `npm run build`。
4. Docker build/up。
5. Playwright 冒烟。
6. `sudo -u mysql git commit`。

最终验收阶段如果没有源码改动，可以用空提交记录验收，但必须在最终说明中明确。

## 不可做的事

- 不泄露或复制第三方 token、Cookie、密码。
- 不把生产密钥放进 Vue、日志、提交或记忆。
- 不用用户未授权的破坏性 Git 操作。
- 不为通过冒烟而删除真实业务逻辑。
- 不把外部商业服务未配置误修成假的本地成功。
